### W3: preferences first (rules in `PathwayPreferences`)

- `GET /pathway/questions`, signed in **and not yet onboarded**: preferences and the profile country answer questions,
  which are left out and listed in `answeredFromPreferences` (question order). Once a pathway profile exists every question
  is returned and the list is empty (the youth is editing).
  - Hours: commitment (max time per opportunity, converted with the course-length study hours) picks the smallest pace whose
    `MaxCourseHours` covers it (≤6 h → 2, ≤15 → 5, else 10).
  - Known skills: any skill on the YoID (self-attested or verified) settles it, mapped by the known-skill patterns.
  - Country: the profile country (it is the profile, not a preference; listed under the same key).
  - Career goal: each goal scores 2 when its `UserGoals` hold the Yoma goal and 1 per preferred category matching its
    `CategoriesPattern`. A unique top goal is **suggested**: listed first and named in the hint. It is skipped only when
    exactly one goal scores and scores ≥ 2 (in practice "Start a business" with nothing pointing elsewhere). "Get a job" maps
    to all five job careers, so on its own it suggests nothing.
  - Background is never in preferences: always asked. A youth with full preferences answers at most two questions (test).
- `PUT /pathway/me/profile`, **lead's rule**: on the first save, for every key the questions endpoint would report in
  `answeredFromPreferences`, the request value is ignored (the web sends fallbacks: `[]`, null, 5) and the preference is
  used; nothing is written back for those keys. Test: `PathwayPreferencesTests.PlanWriteBack_NeverWritesValuesThatCameFromPreferences`
  and `Fill_IgnoresTheWebsFallbacksForHiddenQuestions_AndKeepsTheAskedAnswers`.
- Write-back (only answers the youth gave; add only, never remove; through `IUserProfileService.UpdatePreferences`, every
  other preference sent back unchanged): hours → commitment `Hour × MaxCourseHours` only when unset or a different pace;
  known skills → self-attested skills (first probe name found in the skill lookup) only when no skill of theirs matches;
  career → the first category matching `CategoriesPattern` only when none of theirs matches; Yoma goal → the career's first
  `UserGoals` only when unset. Career, background, country stay in the pathway profile. A write-back failure is logged and
  does not fail the PUT.

### W4: mixed steps

- Each default goal has 5 stages: three learning stages, **a practice stage** (`Types: [ImpactAction, Task]`, `Steps: 2`),
  then the last ("prove") stage; jobs remain the destination. New stage options `Types`, `Steps`; goal options `UserGoals`,
  `CategoriesPattern`, `Destination`.
- The catalogue loads published live Impact Action listings, and `Task` where a database still has that type name (in this
  repo's migrations the Task row `F12A9D90…` was renamed ImpactAction, so `Task` only appears on older data or feeds);
  difficulty from both difficulty custom fields; categories per listing.
- Practice stage with no listing matching its pattern: **lead's rule**, first impact actions related to the rest of the
  path (a skill matching another stage's pattern scores 3, a category matching the goal's `CategoriesPattern` or a picked
  step's category scores 1, then completions, ties by id), with `why` + "These impact actions share skills or a category
  with the rest of your path."; if none, courses matching the stage, with `why` + "No impact action on Yoma fits this stage
  yet, so courses stand in for now."
- Continuation and the drop-off flag are applied to Learning steps only.

### usuallyNext, partnerBadge, dropOff, labels

- `usuallyNext`: from every completed verification (any type), each completer's next completion strictly later; top
  `MaxUsuallyNext` (2) with share and count; hidden below `MinimumGroupSize`; only live steps and jobs are named; cached for
  `CacheInMinutes`. The contract has no note field on `PathwayNextStep`, so the demo note rides on the step's
  `outcome.note` (every catalogue step has an outcome entry that carries `DemoDataNote`). See Requests.
- `partnerBadge`: computed in the catalogue load for every organisation with a step, in three queries (visible Learning
  courses, their grades, their latest assessments), counted like `PartnerBadgeService` and passed to
  `PartnerBadgeCalculator`, so A1's Platinum level appears without a change here. Null only for an unknown organisation.
- `dropOff`: always `{ Collecting, null, "Collecting from the pilot" }`.
- `startLabel` "Finished school · Nigeria" (background label, then the chosen country); `destinationLabel` from the goal's
  `Destination` ("Your first digital marketing job"), else "Your first {goal} job".

### Locks, swaps, alternatives

- `IPathwayStepStore.ListLocked` / `ListSwaps` are read on every build. Locked steps are placed before anything is scored (in
  the stage of their kind they score best in), never trimmed, `locked: true`, ordered after completed and in-progress steps.
  A locked step that is no longer live is left out.
- Swaps replay in order: replaced steps are banned; the replacement goes in the stage its chain's original step held in the
  path built without swaps; swapping back undoes it. Replacements are not `locked`.
- **Alternatives method for A4's controller** (on `IPathwayService`):

  ```csharp
  Task<List<PathwayCourse>> ListAlternatives(Guid opportunityId);
  ```

  Up to `Pathway:MaxAlternatives` (3): same stage and step type, not on the path, not a near-duplicate title of another step,
  best first, fully filled `PathwayCourse` (badge, usuallyNext, dropOff). Throws `EntityNotFoundException` (404) when not
  onboarded or the opportunity is not a step on the path; empty list when there is none. A4's swap endpoint can validate a
  replacement by checking it is in this list (previously swapped-out steps are allowed back).
- 8–12 steps kept (defaults 2+3+3+2+3 = 13, trimmed to 12); same inputs give the same path whatever the catalogue order (test).
