### How Save updates the card

The listing keeps using its existing state: `isOppSaved` in `OpportunityPublicDetails`, loaded by
`isOpportunitySaved(id)` (`GET /myopportunity/action/{id}/saved`) and set to `true` in `saveOpportunity` after
`saveMyOpportunity(id)` (`PUT /myopportunity/action/{id}/save`) resolves. The panel takes `saved={isOppSaved}`, so the
leaving card appears on the same render as the button's "Saved", without a reload. Removing the save hides it again.
The YoID and My Yoma cards call `useJourneyListingSaved` (react-query on the same `GET …/saved`, `staleTime: 0`), because
the global one-hour stale time would otherwise show a stale state after saving on the listing.

## Gotchas

- `NEXT_PUBLIC_*` values are inlined at build time: change them, then rebuild or restart the dev server.
- The `return` URL is built after mount from `window.location.origin`, so the button appears one effect after first
  paint (avoids a hydration mismatch). Behind a proxy, the origin is what the browser sees.
- The saved check only runs for a signed-in user on a published, active listing (existing behaviour); signed out, the
  listing shows the hint, and Yoma's Save asks for sign-in and resumes the save after it.
- The final screen does not need a sign-in: it reads the URL only (there is no shared store, as the contract says).
- The button uses Yoma's CTA style (`bg-blue` with white text), which is under 4.5:1 contrast. It matches the contract
  and the site's existing blue CTAs; the "in progress" state text uses purple for contrast instead of blue.
