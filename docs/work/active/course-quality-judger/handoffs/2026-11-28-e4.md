## What Was Done

- **Local AI, opt-in** (`start.sh --local-ai`; default stays no AI):
  - `docker-compose.demo.yml`: an `ollama` service (`docker.io/ollama/ollama:0.12.3`, profile `local-ai`, no published
    port, healthcheck `ollama list`, `OLLAMA_KEEP_ALIVE=30m`, `OLLAMA_CONTEXT_LENGTH=8192`) and a one-shot
    `ollama-pull` (`ollama pull ${ZIQI_LOCAL_AI_MODEL:-qwen2.5:3b}` against `http://ollama:11434`).
  - Models live in the **external** named volume `yoma-course-quality-demo-ollama-models`, which `start.sh` creates
    (`docker volume create`, idempotent). External, so `stop.sh` and start's reset (`down -v`) keep it and the 2 GB model
    downloads once. `stop.sh` says how to remove it.
  - Hostname: the API has `network_mode: service:gateway`; the gateway is on the `default` network, and so is `ollama`,
    so the API resolves `ollama` by Docker DNS like it resolves `postgres`. No alias needed.
  - The `api` service lists the six `AI__*` variables **by name only** (pass-through from start.sh's environment;
    unset ones are left out of the container, shown as `null` by `compose config`). `start.sh` unsets any stray
    `AI__*` first, runs every start-up check with `AI__Provider=None`, then at the end exports
    `AI__Provider=OpenAICompatible`, `…BaseUrl`, `…Model`, `…IsLocal`, `…TimeoutInSeconds=300` and recreates only the
    API (`compose up -d api`) before the website starts. Reason: on a CPU each AI check takes minutes; with the AI on
    during start-up, the 40-course sample plus events, impact actions and jobs would take hours, and the named courses'
    expected states (keyless) could move.
  - The model pull runs in the background during the build (`compose up -d ollama` first, synchronously, so two compose
    calls never create the network at once; then `compose run --rm --no-deps ollama-pull &`), and start waits for it
    before turning the AI on.
  - `--local-ai-model NAME` (implies `--local-ai`), `--local-ai-url URL` (native Ollama app; start checks it answers on
    localhost, runs `ollama pull` if the CLI exists, else warns if the model is missing). The gateway got
    `extra_hosts: host.docker.internal:host-gateway` so this also works on Linux.
  - `lib.sh` `compose()` and `stop.sh` now pass `--profile local-ai` too, so resets and stops remove the AI containers.
    Services are always named on `up`, so the model server starts only with `--local-ai`.
- **Any OpenAI-compatible server**: `--ai-url URL --ai-model NAME` (mutually exclusive with the local options; both
  required). `IsLocal=false`. A key is read from `ZIQI_AI_API_KEY` and exported as `AI__OpenAICompatible__ApiKey` into
  the script's process only; no file gets it.
- **Events**: `fetch-live-catalogue.mjs --events` → `.cache/live-events.json` (type id `e20dcceb-…`, name `Event` on live
  and here). Ran for real: **17 live events** (totalCount 17), 0 from feeds, 10 with no link. New

## Gotchas

- `ai-smoke.sh` re-assesses the named course with the AI, which can only lower its result: the walkthrough's state of
  that course may change until the next `start.sh`.
- The external volume must exist before `compose up` of `ollama`; start.sh always creates it (empty when unused).
  Running compose by hand with `--profile local-ai` needs `docker volume create yoma-course-quality-demo-ollama-models`.
- Native Ollama on Linux must listen beyond loopback (`OLLAMA_HOST=0.0.0.0`); on Docker Desktop it works as is.
- The key passed with `ZIQI_AI_API_KEY` is visible in `docker inspect` of the API container while it runs (runtime
  environment), never on disk in the repo.
- The ollama container has no memory limit; with the demo's other services Docker needs about 8 GB (start warns).
